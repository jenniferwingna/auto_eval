# MFU 重跑方案（50 条分层抽样，三链同权重同批次）

> 背景：上一轮验证发现 #1、#3 的文本塔前向可能是"全量重放"，而不是原报告假设的"只处理新增 token"；
> 同时原报告的墙钟与 util 来自不同权重的两次跑，行为不一致（108 对 82 个 chunk）。
> 本方案的目的：在**同一权重、同一批样本、同一次运行**里把所有指标一起采齐，使结论可比、可复核。
>
> 规则：
> 1. 不修改任何链路原文件和 `gpu_mfu_calc.py`；插桩用副本或 wrapper，新脚本放 `mfu_rerun/`。
> 2. 只报告测得的原始数字和判定，不要写原因推测。做不到的项写"无法验证"并说明原因，不要用估计值填空。
> 3. 每个 patch 都要加"金丝雀"（canary）：在日志里打印一行证明 patch 真的被调用。上次 vLLM 侧三个挂点 patch 加载了但没命中数据，这次必须先证明命中再采数。

---

## 术语速查

- **增量处理**：每个 chunk 只把新增的 token 送进文本塔，历史靠 KV cache（缓存的中间结果）复用。
- **全量重放（replay）**：每个 chunk 把从开头到现在的所有 token 重新送进文本塔重算一遍。
- **必需计算（用于 MFU）**：按"每个 token 只算一次"的口径，只数新增 token 的计算量。
- **实际执行计算（用于 HFU）**：按真实送进前向的 token 数数，重放的部分也算。
- **GPU·秒/音频秒**：处理 1 秒音频占用了多少 GPU 秒，是最直接的成本指标。

## 第 1 步：抽样

1. 读取 uds_500 每条音频时长，按时长排序，分成 10 个分位档，每档**随机取 5 条**，共 50 条。固定随机种子并记录（建议 `20261124`）。
2. 保存清单到 `samples50.txt`，同时记录：50 条总音频秒数、平均时长、每条的物理 chunk 数（时长 ÷ 0.24 向上取整）、总物理 chunk 数。
3. 校验：这 50 条的平均时长应在全集平均（10.15 秒）的 ±10% 以内。不满足则换一个种子重抽，**并记录一共抽了几次、每次的平均时长**，不要只留最后一次。

## 第 2 步：插桩内容（每条链都要）

对每一次文本塔前向调用，记录一行：

```
chain, run_id, sample_id, chunk_idx, 本次送入文本塔的 token 总数, 其中新增 token 数（若可区分）,
KV cache 当前长度（若可取）, 音频塔本次输入行数（若有）, 本次调用起止时间戳
```

各链要点：

- **#1**：沿用上次 hook 方式（`forward_step`、`_run_tower`），新增 token 数 = 本次序列长度 − 上次序列长度。
- **#2**：沿用 `decode_step_batch`、`prefill_batch`。额外记录**每个样本在音频结束后又处理了多少个 chunk**（即静音尾），分开计物理 chunk 与尾部 chunk。这用来对账：上次验证里同批 20 条的 census 是 1,969 个 chunk，而报告引用的是 59,126。
- **#3（重点）**：目标是**直接**看到引擎实际执行每步时送进模型的 token 数。
  - 在引擎核心进程（engine core / worker 进程，而不是客户端或 API 进程）里的 `model.forward` 外层包一层，把 `input_ids` 的长度写入**按进程号命名**的日志文件。
  - 先确认 patch 在该进程内生效：启动时写一行 canary，首次调用再写一行。
  - 备选读数来源（按优先级）：vLLM 日志里的每步统计、`/metrics` 接口里的迭代 token 直方图类指标。先确认当前版本（0.26）实际暴露了哪些指标，再用。
  - 如果以上都做不到，写"无法直接验证"，并只提供第 5 步的辅助证据。

**判定标准（#1、#3 各自）**：把"本次送入 token 数"按 chunk 序号分档（0–9、10–19、20–39、40–79、80+），报告每档均值。
- 各档接近且在 12–13 附近 → 增量处理。
- 随档位明显增长、斜率接近每 chunk 11–12 token → 全量重放。
- 其他形态：原样报告，不要强行归类。

## 第 3 步：正式运行

**运行矩阵**：每条链在同一批 50 条上运行 **3 次**（正式计入），每条链正式运行前先用 5 条样本预热 1 次（不计入）。
三条链**依次**运行，不并行，顺序交错（例如 #1、#2、#3、#3、#2、#1、#1、#2、#3），避免时间漂移偏向某一条链。

**配置**：各链用其日常生产配置，并把配置原样记录：#1 串行；#2 的批大小与卡数；#3 的并发数。
额外加一组 #2 单卡运行（如果脚本支持），用于和 #1、#3 在相同卡数下比较。

**每次运行同时采集（同一时间窗）**：

1. **墙钟**：统一口径为"第一条音频送出 → 最后一个结果收到"，**不含模型加载**。模型加载耗时单独记录（#2 的墙钟原先含加载）。另外各链保留自己的原口径墙钟（如 #1 的 generate-only）用于对账。
2. **util 与功耗/时钟**：`nvidia-smi --query-gpu=timestamp,index,utilization.gpu,power.draw,clocks.sm --format=csv -lms 500`，只采本次用到的 GPU，写入带时间戳的 csv。计算均值时，只取墙钟起止时刻之间的行，起止时刻来自第 1 条记录。
3. **token 日志**（第 2 步）。
4. **输出**：每条样本生成的词数、文本，用于核对三链工作量是否一致。

## 第 4 步：指标计算（新写独立脚本）

**输入常量**（从 config 与实测读取，不写死）：N_active = 2.718e9、`num_experts_per_tok`（确认是 8）、hidden、vocab、层数、峰值 989.4e12。
音频塔每次前向 FLOPs **采用 V2 实测值 41.98 GF**（比原报告公式 32.82 GF 更准）。

**输出两列**：

| 列 | 文本塔 token 数取值 | 含义 |
|---|---|---|
| 必需计算 → **MFU** | 只取新增 token | 每个 token 只算一次的计算量 |
| 实际执行 → **HFU** | 取真实送入前向的 token 数 | 包含重放的计算量 |

两列都包含：文本塔线性层（2 × N_active × token）、注意力（用该次真实上下文长度）、lm_head（按生成词数）、音频塔（41.98 GF × 前向次数）。
MoE 专家部分 FlopCounterMode 数不到，用公式计算，并在报告里标注"公式值，未经算子级实测"。

**分母**：墙钟（第 3 步统一口径）× 实际使用的 GPU 数 × 989.4e12。

**同时输出**：
- GPU·秒/音频秒 = 墙钟 × GPU 数 ÷ 50 条总音频秒
- RTF = 墙钟 ÷ 50 条总音频秒（单流链）
- util 均值
- 词率（词数 ÷ chunk 数）与每条链的总生成词数

## 第 5 步：#3 的辅助证据（仅当第 2 步无法直接观察时必做，否则可选）

1. concurrency=1，选 5 条不同长度的样本（物理 chunk 数分布在 10–120），记录每条的墙钟，拟合 `T = a·c² + b·c + d`，报告系数与拟合优度。
2. 用 torch.profiler（或 nvidia-smi 采样做不到的就写不能）在一条长样本上记录**每个 chunk 的 GPU kernel 总时间随 chunk 序号的变化**。增量处理应是平线，全量重放应上升。

## 第 6 步：重复性与"可区分"的判定

- 每条链 3 次的墙钟，报告均值、最小、最大、（最大−最小）÷ 均值。
- 声明"链 A 与链 B 的差异可区分"，只在两链均值之差 **大于两链各自组内波动的 2 倍**时成立，否则写"不可区分"。
- 上次 #3 的波动是 14.3%，#1 是 1.3%，请继续按此标准判定。

## 第 7 步：外推到 500 条（只做 #1）

#2、#3 有批处理和并发，样本间耗时不可相加，不要外推。#1 是串行，可以：

1. 用 50 条数据拟合每条样本耗时 `T(c) = a·c² + b·c + d`（c 为该条物理 chunk 数）。
2. 用 uds_500 全集每条的 chunk 数代入求和，得到 500 条预测总耗时。
3. 与报告里已有的 500 条结果（7436.6s，注意那是另一份权重）并列展示，**不要用它去校准**，只作为数量级对照。
